# v2 发布准备与可自动验证的检查

2026-10-30。对应路线图 M5 后的“v2 发布检查/云端补验”，不新增 M6，也不增加产品执行权限。此阶段交付本地检查、运行包、完整性校验、独立目录冒烟和 CI；真实模型、正常定时成功结果、目标 Linux/HTTPS/2核2GB 的缺口继续保留。

## 1. 本地检查和生成运行包

在完整源码仓库、Node 24.16+ 且小于 25、已安装锁定依赖的环境执行：

```sh
npm run release:check
npm run release:pack
```

`release:check` 先核对文档 SHA，再验证并清理两个固定生成目录 dist 与 frontend/dist，依次执行 typecheck/build/test，最后检查运行包布局和引用的前端资源。清理不会触及数据目录；发现符号链接或越界路径时拒绝清理。

检查记录保存在忽略目录 `data/releases/check.json`。它包含 Commit、源码/配置/测试/文档输入摘要、构建产物摘要和检查状态，不含真实配置、原始日志或凭据。检查期间修改源码会失败；检查后修改源码、Commit 或构建产物，必须重跑。打包还要求工作区干净，防止混入未审阅修改。

`release:pack` 生成 `data/releases/scout-<version>-<commit>-<digest>.tar.gz`、同名 `.sha256` 及 `latest.json`。相同输入、构建及同一检查记录可重复生成相同包；重新执行检查的耗时记录可能不同，不能只凭相同 Commit 断言压缩包逐字节相同。

这是运行候选包：包含 dist/server、frontend/dist、migrations、scripts、deploy、当前/历史设计 Markdown、package.json/lock、README、MANIFEST 和 `.env.example`。不包含真实 `.env`、数据库、日志、node_modules、源码树、测试夹具或历史运行证据。运行包不是源码开发包，不能在其中重新执行依赖源码的 build/typecheck/test。

## 2. 完整性校验与解压

```sh
npm run release:verify -- data/releases/<archive.tar.gz>
npm run release:extract -- data/releases/<archive.tar.gz> data/releases/new-install
```

先核对压缩包 SHA（同名校验文件存在时自动检查）、逐文件字节数/SHA、清单与必要布局，再写入全新目录。拒绝覆盖已有目录、路径跳转、绝对路径、符号/硬链接及特殊 tar 类型、大小超限、重复/大小写冲突项、缺失或改动文件。

包内 RELEASE-MANIFEST.json 不列自身，其他载荷均列入清单；外层 SHA 覆盖整个包。SHA 用于内容完整性，**不是来源签名或供应链身份认证**；来源仍需核对可信仓库/CI 和 Commit。整个包上限 64MiB、最多 3000 文件，不能借压缩绕过读取上限。

## 3. 从包中启动冒烟

```sh
npm run release:smoke -- data/releases/<archive.tar.gz>
```

本地模式先校验、解压到全新临时目录，只链接本机已有的正式直接依赖，然后在单 Node 进程内启动包中应用。使用随机密码、独立临时数据库、回环随机端口；不读取现有数据库，不加载私有 `.env`，不触发发现/分析/补丁。所有外部 fetch 请求被拒绝，成功和失败都恢复工作目录/网络函数并清理自建临时目录。它运行可信的本项目构建，不是不可信包的执行沙箱。

检查健康、页面和资源、管理员权限、Origin/CSRF、登录/退出、默认关闭的发现/评估、无调用的诊断、空存储与迁移。结果在 `data/releases/smoke-<commit>.json`。`LOCAL_REUSE` 只证明当前平台借用依赖后可运行，`productionInstallValidated=false`；不能据此宣称 Linux 原生模块安装成功。

CI 使用不同路径：

```sh
npm run release:extract -- data/releases/<archive.tar.gz> data/releases/installed
npm ci --omit=dev --prefix data/releases/installed
npm run release:smoke -- --installed data/releases/installed
```

installed 模式检查 npm 实际安装清单不含 dev 包、正式直接依赖版本与锁定值相符，再运行同一组冒烟。即使 Linux runner 成功，也不证明目标服务器的 HTTPS、systemd、权限和 2GB 容量达标。Windows node_modules 不随包复制到 Linux。解压器默认目录 0700、文件 0600，适合私有暂存；正式安装到 root 管理的 /opt/scout 前，应按部署用户/组设置目录可读可遍历（例如 root:scout、0750）和文件只读权限（例如 0640）。不要直接把 root 的私有暂存目录当成 scout 已可读取的安装目录，配置文件仍按部署文档单独保存。

## 4. 生产配置预检

构建后显式提供私有配置文件的路径，真实内容留在本机/服务器：

```sh
npm run deploy:check -- /etc/scout/scout.env
```

该命令只解析最多 64KiB 的指定文件，不写环境、数据库或磁盘配置，不联网。检查 production 模式、现有配置规则、有效限额、回环 HOST=127.0.0.1、与随包 Caddy 一致的 PORT=3000、非默认示例 HTTPS 源、systemd 可写范围内的绝对 DB_PATH（/var/lib/scout/）。输出仅是字段检查状态与默认密钥引用存在布尔，不输出值、长度、前后缀或密钥 hash。

它不能证明密钥有效、默认引用就是数据库当前自定义引用、域名可访问、文件属主/权限正确或服务能启动。仓库 `.env.example` 使用占位 hash/示例域名，预检失败是预期行为。没有真实配置文件时只通过夹具验证工具，不制造“生产配置已通过”的结论。若修改 Caddy 端口/可写目录，需要同步调整预检和部署材料。

## 5. 本地通过与生产就绪分开

`release:check` 成功退出只说明本地验证通过，所有候选包/报告仍明确 `productionReady=false`。若调用：

```sh
npm run release:check -- --require-ready
```

会完成本地检查，并因尚无真实验收证明以 **退出码 2** 拒绝就绪成功。这是预期门禁，不是构建失败。CI 不使用此选项，只产出候选包，不发布 GitHub Release、不合并、不部署或公开报告。

尚需按 [验收标准](验收与发布标准.md) 补齐 M4 真实模型闭环、M5 正常定时成功候选/最终同窗口复核，以及目标 Linux/HTTPS/2核2GB（含发现负载）、备份恢复等。可选发现模型单独记录，未启用时 NOT_RUN。不从历史 Markdown 自动推导 PASS，也不把上传 CI 制品当作通过真实验收。

## 6. CI 与交付

CI 覆盖 main、feat/**、fix/**、codex/** 及 PR：本地检查 → 打包/校验/新目录解压 → Linux 正式依赖安装 → 包内冒烟 → 上传候选包与检查摘要，保存 7 天。CI 状态须以 GitHub 实际结果为准。

Action 版本按 2026-10-30 官方用法核对：[checkout](https://github.com/actions/checkout)、[setup-node](https://github.com/actions/setup-node)、[upload-artifact](https://github.com/actions/upload-artifact)。应用依赖版本保持现有锁定，无新生产依赖。

验收与合并材料见 [发布准备记录](../evidence/v2-release/验收记录.md)、[中文合并说明](../evidence/v2-release/合并说明.md)。历史 M0–M5 证据不改写。
