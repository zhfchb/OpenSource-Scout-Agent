# OpenSource Scout Agent 分阶段开发计划

版本：1.0｜2026-10-29｜状态：实施计划，不代表任务已完成。

实施依据：[PRD](产品需求文档.md)、[ARCHITECTURE](技术架构.md)、[DECISIONS](设计决策记录.md)。先完成核心闭环，再完善运营能力。M0—M5为MVP；V1-A—V1-D为V1；Future不纳入当前交付。

## 1. 执行规则与完成定义

每阶段输出可运行增量、验证证据和已知限制。未通过上一阶段硬门槛，不启动依赖它的高风险能力；允许先做不依赖该能力的只读分析。不得因展示需求将模拟数据装成真实运行，不得因沙箱未完成在宿主机执行目标仓库代码。

每个任务完成须满足：需求ID可追踪、实现可运行、适当测试通过或明确阻塞、配置/迁移/使用说明更新、无凭据进入仓库和日志。每个阶段报告实际执行命令、测试结果、未执行项、制品和剩余风险；不以“文件已生成”代替验收。

以下工作量是个人开发排期的建议区间，不是交付日期承诺；不包含等待维护者、云资源和审批的时间。每阶段完成后按实际结果重估后续范围。

## 3. M0：工程与边界基线

**目标**：Codex先理解设计，建立最小可验证工程，不一次性生成全部功能。

任务：

- 审查五份文档，列出矛盾、必要待定项和实施建议，建立实施任务清单；可逆细节直接给出默认方案并记录。
- 检查实际目录、已有代码、AGENTS.md、Git状态和开发环境，避免覆盖现有工作。
- 初始化建议目录与配置schema、密钥引用、结构化日志、健康检查、数据库迁移入口、CLI入口。
- 建立Windows开发/Linux生产的Compose骨架，区分控制面与Runner；无隔离前执行工具默认禁用。
- 锁定经兼容验证的依赖版本，记录Python、LangGraph、Checkpointer适配器和数据库版本。
- 准备一个固定Python样例仓库、一个固定Java样例仓库及恶意输入夹具；标记为测试数据。

交付：最小可启动应用、示例配置、环境说明、任务清单和威胁边界说明。

验收：干净配置可启动健康检查与CLI；缺少模型/GitHub凭据时有清晰提示且不泄漏；无沙箱时拒绝执行；数据库可建库与迁移；日志种入测试secret后输出中不存在明文。

覆盖：F12、F16的工程基础；决策7、10、17、18、31。

## 4. M1：状态、任务、Checkpoint与预算

**目标**：先让无副作用工作流具备持久性，后续Agent节点接入相同契约。

任务：

- 建立MVP核心表、三层状态、不可变配置与制品引用。
- 实现APScheduler只入队、单Worker领取、租约续期、generation fencing与取消。
- 用无外部副作用的LangGraph节点验证持久化中断/恢复，设计领域表与Checkpointer对账。
- 实现任务/阶段幂等键、唯一约束、attempt与事件日志、错误分类与有限重试。
- 实现每日/任务Token与调用数预算、原子预留、结算与暂停；价格缺失时禁用伪精确金额。
- 加入制品写入提交协议、孤立制品识别和恢复工具。

验收：

1. 同一逻辑任务重复触发10次，只有一个任务记录，事件无重复逻辑提交。
2. 节点输出落盘前后、领域提交前后分别杀进程，恢复不丢已提交结果；pending制品可对账。
3. 旧Worker在租约过期后提交被拒；取消、等待批准、预算暂停均不占租约。
4. 新配置不改变运行任务；Checkpoint不兼容时明确拒绝直接恢复。
5. 并发预算申请不能超额；usage未知记为未知，超时占用有对账路径。

交付：恢复演练记录、状态/预算测试、可重复的故障注入脚本与真实结果。

覆盖：F11、F12、F14；决策6、7、11、12、15、16、26。

## 5. M2：发现到证据充分的机会

**目标**：真实GitHub只读路径完成到READY_FOR_APPROVAL。

任务：

- GitHub只读适配器：认证引用、分页、ETag、限流、超时、资源重命名、PR/Issue区分。
- 项目搜索、动态项目池、技术画像/排除规则、增量游标与默认周期复核。
- L1规则过滤与可配置评分；模型网关单模型结构化接口与用量记录。
- L2按需拉取Commit固定的相关源码，输出E0—E3证据、风险、变更计划及验证方案。
- 独立评分引擎、版本化重评、需求型与缺陷型机会区分。
- 通过CLI确认计划；证据不足保持调查，不进入补丁生成。

验收：固定响应夹具验证429、5xx、分页中断和重复抓取；一条真实公开Issue生成可人工核实的源码链接与报告；重新评分不再调用源码分析；第二个模型赞同不能将猜测提升为E2；配置更新仅用于新任务；Issue已被解决/存在重复PR时提示并停止推荐提交。

交付：真实分析报告、证据包、分项评分、已知数据缺口及API消耗记录。公开引用的Issue内容和测试夹具应遵守原项目许可及平台规则。

覆盖：F01—F06、F12、F14；决策2、3、4、12、13、14、24、25、27。

## 6. M3：隔离执行与验证

**目标**：沙箱边界经实测后才允许执行第三方代码。

任务：

- 实现隔离Worktree与路径校验，任务目录/分支确定性命名；保留Diff和基线。
- 实现窄接口Sandbox Runner和可信镜像digest，限制CPU、内存、PID、磁盘、超时、权限与网络。
- 提供Python、常见Java模板；依赖准备与离线执行分开；项目Dockerfile/CI只作为环境识别数据。
- 实现T1—T4报告契约，MVP着重T1/T2，T3/T4不支持时明确标识；保存基线测试与修改后测试。
- 执行恶意仓库测试：越界路径/符号链接、内网/元数据访问、密钥读取、Docker socket、资源耗尽、恶意构建脚本。

验收：Python与Java各完成一条可重复局部测试；宿主/应用凭据不可见；网络与资源攻击被阻断且应用继续健康；环境缺失为ENVIRONMENT_UNAVAILABLE，静态通过不提升为单元通过；无沙箱时执行被拒，不能自动回退宿主机。

交付：镜像清单与摘要、允许命令模板、隔离测试证据和环境能力矩阵。

硬停止点：任何越权执行或secret泄漏未解决，不进入自动动态验证和后续公开部署。可继续只读分析与修复隔离问题。

覆盖：F07、F08；决策5、9、10、17、28、29。

## 7. M4：补丁到人工审核闭环

**目标**：在已批准计划内生成补丁并交付可信审核包。

任务：

- L3补丁生成，强制计划范围和证据门槛；敏感变更/新依赖升级风险并重新审批。
- 独立审查节点检查必要性、副作用、覆盖和范围；生成节点不自行批准自己的产物。
- 有限修复循环：代码修复默认2次，基础设施重试独立计数，保留每版Diff/测试。
- 门禁实现PASS/NEEDS_DISCUSSION/BLOCKED及所有检查项的原因、证据、豁免范围。
- 审核绑定具体Diff和基线；MVP导出Patch、测试报告、PR草稿和人工提交说明。
- 支持回填PR URL、同步Issue/PR/Review/CI事实、原始反馈存档。

验收：真实Issue至少完成一条“定位→计划批准→补丁→适当验证→独立审查→人工审核”路径；修改范围超限使批准失效；失败补丁不被PASS；2次代码修复后停止；远端基线变化触发重验证；MVP不使用任何GitHub写凭据、不调用写API；人工提交后的PR可追踪，但是否合并不作为此阶段门槛。

交付：一份真实审核包、一份失败或环境阻塞包、状态及门禁测试结果。

覆盖：F07—F10、F14、F15；决策1、5、9、15、16、22、23、27、28、29。

## 8. M5：真实只读展示、评测与MVP发布

**目标**：别人可访问真实成果，自部署者可复现基础流程。

任务：

- 最小历史只读站点：机会列表、运行时间线、证据、Diff与测试摘要；先实现信息真实性，不做复杂实时动效。
- 内部事件到公开投影的白名单脱敏、制品扫描、管理员预览/批准发布与撤回。
- 10—20条起步人工标注集、冻结输入、开发/留出拆分和基线评测；明确小样本限制。
- Linux Compose部署、HTTPS与管理入口限制、健康/磁盘/预算监控、备份恢复演练。
- 自部署README、配置示例、密钥说明、支持环境、故障排查、开源许可选择清单。

验收：访客无任何运行/管理权限；注入测试secret/路径/个人信息后公开页面、API、下载制品中均无泄漏；演示数据与真实运行明确区分；至少一条真实历史运行和一个失败案例可审计；备份恢复后事件与制品哈希一致；全部F01—F16有验收结论及证据，不支持项不能标完成。

交付：MVP版本、公开演示入口（实际部署后填写）、真实报告、评测报告、运维和恢复说明。没有实际部署不得提供虚构URL；未完成HTTPS/权限验证不得宣称公网发布完成。

覆盖：F13、F15、F16；决策8、18、19、20、21、30、31。

## 9. V1阶段

### V1-A：管理后台与SSE

增加画像、模型、评分、预算、项目池、任务和审批管理；使用服务端鉴权与配置版本；公开SSE与私有管理事件流分离，Last-Event-ID补发、去重、过期恢复、限速和撤回生效。

验收：陌生访客不能访问管理配置或触发任务；两次并发编辑能检测版本冲突；SSE断线期间事件可补齐；历史投影与实时事件同一脱敏规则；运行未批准公开时不能订阅。覆盖F17、F18。

### V1-B：Postgres、pgvector、Redis与多Worker

先迁Postgres及Checkpoint并完成回退演练，再引入Redis与多个Worker；结构化记忆为主，按需引入pgvector检索分析/经验；索引故障不得影响基本流程。

验收：停写迁移校验完整；两个Worker争抢同一任务仅一方可提交；Redis重启/消息重复/消息丢失不丢任务；旧Worker不能覆盖新结果；不同模型维度向量隔离；数据库故障后恢复演练通过。覆盖F19、F20存储基础。

### V1-C：模型路由、探索、动态调度与反馈记忆

实现任务类型模型路由及受控回退；源码主动发现预算；机会价值/时效/成本/等待时间组合优先级；原始反馈→仓库经验→通用经验，可信度、TTL、撤销和版本关联；经验用于评分、生成、门禁但不修改权限。

验收：过期源码结论不作为当前事实；恶意评论无法授权工具；低优先级有老化策略；所有探索受全局硬预算约束；相同留出集对比基线，报告收益及成本，不承诺必然提升。覆盖F20、F21及模型路由。

### V1-D：外部写入与V1发布

增加独立写凭据、逐动作批准、内容哈希、过期失效、远端对账与outbox；必要时再引入GitHub App，PAT不是必须替换。fork、push、PR创建及评论分别记录权限和批准。

验收：无批准/过期/Hash变化/门禁阻断时拒绝；模拟写入超时后先核对远端，不重复PR；UNKNOWN无法查明时停等人工；LLM/Runner/公开端均拿不到Token；取消或基线变化能撤销尚未执行的写操作。使用测试仓库验证后，真实仓库写入仍逐次人工批准。覆盖F22。

V1发布条件：F17—F22均有证据；重新运行MVP关键回归、安全和故障注入；提交评测与成本报告；升级/回退文档可复现。若选择拆小版本，明确标注尚未交付能力，不能提前宣称完整V1。

## 10. Future：独立评审后才立项

更多平台、语言与运行环境，高级模型效果评估、Langfuse等平台接入、对象存储、多执行机弹性，以及可能的协作模式。公共SaaS与多租户不是默认发展方向，若提出需重新设计隔离、授权、配额、账单与滥用边界。

## 12. 风险与调整策略

| 风险 | 触发信号 | 处理 |
|---|---|---|
| 范围膨胀 | 前端/多Agent先于闭环 | 回到M2—M4关键路径，延期高级能力 |
| 环境兼容成本过高 | 大量任务卡依赖 | 收敛可信模板，明确环境不可用，不放宽隔离 |
| 源码分析成本过高 | 高Token低有效机会 | 减少L2配额、优化L1/上下文选择，先评测再扩容 |
| 机会质量低 | 人工审查误报多 | 校正评分/证据门槛与画像，保留失败样本 |
| 公开信息泄漏 | 投影/下载出现敏感内容 | 立即撤回和修复；公开发布暂停，内部开发继续 |
| 不确定外部写结果 | 超时后无法核对PR | 标UNKNOWN等待人工，不重复写 |
| 多Worker竞态 | 重复提交/旧任务覆盖 | 暂回单Worker并修fencing，对账后再扩容 |
