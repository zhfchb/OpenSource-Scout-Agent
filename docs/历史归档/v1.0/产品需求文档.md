# OpenSource Scout Agent 产品需求文档

版本：1.0｜日期：2026-10-29｜状态：待实施的设计基线，不代表功能已经完成。

配套文档：[架构](技术架构.md) · [路线图](开发路线图.md) · [31项决策](设计决策记录.md) · [Codex启动提示词](开发启动提示词.md)。

## 1. 来源、约束与解释规则

依据用户提供的[完整讨论](https://chatgpt.com/share/6ae2c053-d61c-83e9-bf64-777e64a5d6a7)及本次任务。原31项决策按原编号记录于 设计决策记录.md。本文中具体字段、接口、验收数量和资源默认值是为可实施性补充的设计基线，不冒充历史对话原文。

后期决策优先于早期宽泛设想：第31项要求核心闭环优先；第18—20项要求公网只读展示真实轨迹；第8项将完整管理后台放在V1。故MVP包括CLI、报告和最小只读展示站点，不包括完整后台。第15项保留开发前确认；第16项允许有限自主修复，不等于默认取消开发前确认。第27项的证据门槛与人工确认须同时满足。

## 2. 产品定位与目标

为个人开发者持续发现适合自身技术画像的开源贡献机会，将GitHub项目发现、Issue评估、代码定位、补丁生成、安全验证及人工审核串成可追溯闭环。网站向访客展示经审核的真实过程和成果；源码开源，其他开发者可独立自部署。

主要用户为实例所有者；访客只能阅读已公开数据；自部署者拥有自己的独立实例。不是多租户SaaS，不开放访客运行Agent、上传仓库、配置模型或消耗实例凭据。

成功标准：真实机会有出处；分析有版本化证据；补丁有Diff与适当验证；外部写入受控；失败可解释、可恢复；公开展示不伪造结果。PR合并是外部结果指标，不作为软件发布的硬性前提。

## 3. 版本范围

| 能力 | MVP：可验证闭环 | V1：持续运营 | 未来，非V1承诺 |
|---|---|---|---|
| 发现 | GitHub动态项目池、Issue优先、允许人工加入项目 | 有预算的源码主动发现、技术画像探索比例 | 更多代码托管平台 |
| 分析 | L1筛选、L2证据定位、L3补丁；LangGraph有界流程 | 更丰富语言/项目适配与模型路由 | 更广领域自主探索 |
| 操作 | CLI管理、开发确认、补丁审核、手工提交PR | Web后台、受批准的GitHub写工具 | 多人协作需另立设计 |
| 展示 | 基础只读网站、历史轨迹、报告、管理员选择发布 | SSE实时脱敏事件与历史回放 | 高级可观测性平台接入 |
| 存储 | SQLite、结构化历史、文件制品 | PostgreSQL、pgvector按需语义检索 | 独立对象存储按容量引入 |
| 任务 | APScheduler、持久化任务表、单Worker、基础优先级 | Redis投递、多Worker、老化与细粒度配额 | 集群弹性调度 |
| 记忆/评测 | 原始反馈记录、版本化证据、小型人工评测集 | 仓库/通用经验、反馈闭环、对比评测 | 自动化策略优化 |
| 环境 | Python和常见Java可信模板，静态/局部验证 | 按风险增加集成验证环境 | 更复杂完整环境与隔离技术 |

MVP不直接调用GitHub写API；审核后导出Patch、分支说明和PR草稿，由所有者自行提交并回填PR URL。这样形成到人工审核的产品闭环，并可继续跟踪贡献结果。完整贡献闭环包含人工提交，不声称自动提交已实现。

## 4. 核心用户旅程

1. 所有者配置技术画像、GitHub只读凭据引用、模型、预算和项目过滤条件。
2. 手动触发或定时发现项目；系统记录候选、过滤原因和项目池状态。
3. 增量获取Issue、PR及目标Commit；L1规则筛选后选择少量机会进入L2。
4. L2定位源码并输出证据、评分、建议变更计划和测试方案；不足则继续调查或暂停。
5. 所有者确认开发范围；系统创建隔离Worktree、生成补丁，进行独立审查与最小充分验证。
6. 失败时按类型重试或至多两次代码修复；成本或次数到限即停止。
7. 门禁给出PASS、NEEDS_DISCUSSION或BLOCKED；所有者审核Diff与验证报告。
8. MVP导出材料后人工提交；V1可批准绑定具体内容的受控写操作。系统同步PR/Issue事实。
9. 所有者预览脱敏轨迹并发布；后续反馈作为有来源、有时效的参考数据。

### 5.1 评分契约

硬过滤先于评分：排除项目、明显重复/已解决Issue、无法满足安全策略的任务不得靠高分放行。建议分项为项目活跃度、技术匹配、贡献价值、问题可信度、可实施性与维护者可接受性，统一归一到0—100。权重非负且总和为1；缺失项列为未知，并输出覆盖率；默认用保守值参与，不静默删项后重分配权重。

规则分与LLM分开保存，合成比例可配置。LLM只提供结构化建议，不能更改硬门禁。数值置信度仅是系统估计，不宣称为统计概率。初始权重及阈值均为实施默认值，在评测后调整。

### 5.2 证据与验证是两个维度

| 证据级别 | 定义 | 处理 |
|---|---|---|
| E0 | 仅AI猜测 | 调查，不自动生成补丁 |
| E1 | 源码位置与触发条件 | 补独立证据 |
| E2 | 有独立证据支持，如规范、调用路径、已有测试/维护者确认 | 可进入补丁候选，但仍需计划批准 |
| E3 | 成功复现，保留输入、命令、环境和结果 | 优先处理；仍需验证补丁 |

第二个LLM重复同一猜测不自动构成E2。明确需求任务以Issue需求、确认的行为契约和验收用例作为依据，不硬套E3。

验证层级使用T1—T4，避免与分析L1—L3混淆：T1静态，T2编译/单元/Mock，T3集成，T4完整环境/E2E。按修改风险选择最小充分方案，不要求完整运行每个项目。即使编译也可能运行构建脚本，必须隔离。

每个检查项的结果为PASSED、FAILED、NOT_RUN、ENVIRONMENT_UNAVAILABLE、TIMED_OUT或CANCELLED，另存类型STATIC/COMPILE/UNIT/INTEGRATION/E2E。不能把静态通过写成项目测试全通过；未执行不能计入通过率。

### 5.3 PR门禁

PASS：适用的必要检查均通过，证据及范围有效，外部状态已刷新。NEEDS_DISCUSSION：需求/贡献意向不清、可接受的验证缺口待人工判断。BLOCKED：安全违规、必要测试失败、未经批准的敏感变更、已存在等价修复等硬阻断。

NEEDS_DISCUSSION不直接提交PR；先记录讨论或管理员对可豁免项的理由，再重新评估。安全硬阻断不可豁免。缺少环境不等同代码失败，但若缺失的是必要验证，不能PASS。MVP门禁输出同样用于人工提交材料，不能借手工导出宣称已通过。

## 6. 交互、权限与公开范围

MVP CLI必须支持discover、scan、analyze、approve-plan、patch、validate、review、export、link-pr、publish、cancel、resume等等价能力，不限定具体命令拼写。所有变更有操作者与审计记录。后台可先通过私有网络/本机访问；公开路由与管理路由分离，管理权限由服务端强制检查。

访客可见：公开项目名/链接、Issue、允许公开的Commit、证据摘要、分项评分、真实节点时间线、脱敏工具摘要、补丁与测试摘要、PR状态及最后同步时间。内部原始Prompt、原始模型响应、凭据、个人信息、宿主机路径、未审核日志、内部异常堆栈默认不公开。公开内容采用字段允许列表，不依赖前端隐藏。

“完整轨迹”指可审计的节点和工具执行事实，不是模型隐藏思维链。公开制品也必须经过内容审核与脱敏。撤回后服务端与缓存停止提供数据；已被外部下载的内容无法收回，发布前应预览。

## 7. 非功能需求与发布验收

以下为项目建议验收门槛，不是原对话承诺或已测性能。

- 可靠性：对同步、L2完成、补丁保存、验证完成四个位置注入崩溃后均可恢复；同一逻辑任务重复触发10次无重复机会/分支制品；恢复允许重复LLM调用但须记录成本风险。
- 安全性：恶意仓库读取密钥、访问内网、越界写文件、启动特权操作均被拦截并留证；公开接口种入测试密钥及个人信息后无泄漏；无沙箱执行能力时降级为静态报告。
- 可追溯性：任何评分、补丁和批准可反查repo/Issue、Commit、配置、模型、Prompt模板版本和相关证据；公开每条成功事件都能定位内部真实事件。
- 可控性：每天预算、单任务Token/耗时/磁盘、最大修复次数和并发有上限；成本统计滞后时使用预留和保守估算保护硬上限。
- 性能：验收环境记录硬件与样本；基础公开列表20条时建议服务端P95不超过2秒，排除LLM执行时间；未满足时先记录瓶颈，不虚构达标。
- 运维：健康检查区分Web存活与Worker/调度可用；备份包含数据库、Checkpoint与制品；恢复演练验证哈希和引用关系。

MVP发布需：一条真实公开Issue路径完成到人工审核；Python与Java模板各有可验证样例（可用固定测试仓库，但明确区别）；至少一个失败/环境不可用案例可展示；所有F01—F16验收逐项留证；安全与可靠性硬门槛通过。PR是否被维护者合并不阻塞发布。

## 8. 评测与指标定义

初始建议10—20条人工标注真实Issue，保存冻结Commit、标签标准、证据和许可/来源；这只是起步规模，不能据此做总体能力结论。开发集与留出集分离；模型、Prompt和评分策略对比使用相同冻结输入。历史已解决Issue需避免把答案直接提供给生成步骤，记录可能的训练污染。

| 指标 | 分母/口径 |
|---|---|
| 运行完成率 | 成功终结的执行 / 具备执行条件的已启动执行；另报取消、限额、环境阻塞和系统错误 |
| Precision@K | 人工认为有贡献价值的前K候选 / 实际审查的前K候选；记录标注分歧 |
| 补丁有效率 | 经预定回归验证且人工认可的补丁 / 已完成评审的生成补丁；环境阻塞另列 |
| 门禁准确性 | 人工复核门禁误放/误拦数量及理由 |
| PR合并情况 | 已合并 / 已提交PR，同时报告待决、关闭未合并、观察窗口；不得只展示成功样本 |
| 成本 | 每任务/有效机会的Token、调用数、耗时与估算费用；缺失usage单列 |
| 恢复可靠性 | 故障注入成功恢复数 / 注入数；重复副作用单列 |

## 9. 风险、依赖与边界

GitHub限流/权限变化由适配器处理；模型幻觉靠证据契约、独立审查及人工审核控制；第三方仓库是恶意输入边界；构建工具与依赖供应链同样不可信。Docker隔离不是绝对安全保证，执行面需与带密钥控制面分离。

项目环境差异通过可信模板及明确降级处理，不承诺任意仓库自动跑通。维护者响应和合并意愿不可控。预算不足应减少项目、深度或频率，不能移除安全门槛。MVP不做向量数据库、多租户、复杂实时前端或不受控自动PR。

## 10. 可实施的默认假设

技术框架和资源数值以技术架构.md为建议基线；实施前检查真实环境和官方API兼容性，锁定依赖后记录，不凭文档猜测最新版本。开源许可证、域名、生产机器规格、模型供应商及每日金额预算未在讨论中最终指定：可先用示例配置开发，正式公开源码/部署前由所有者填定；不阻塞本地M0—M4开发。
