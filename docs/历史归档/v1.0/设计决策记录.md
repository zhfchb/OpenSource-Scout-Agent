## 3. 关键补充的保留方式

### 3.1 开发确认与自动补丁的关系

D15定义READY_FOR_APPROVAL及“批准生成补丁”，D16允许有限自主修复，D27要求E2/E3门槛。本文不把后两者解释为取消开发确认：证据合格仅表示可申请进入补丁阶段，MVP仍由所有者确认计划。未来若允许指定风险范围的预授权，应另立决策、限定仓库/范围/预算/期限，不自动启用。

### 3.2 MVP网站与V1后台

D08的MVP先CLI/报告与D18—D20的公网展示通过最小只读历史网站兼容。MVP站点是对真实报告与事件的发布投影，不是完整控制台。V1才增加管理后台和SSE。基础公开展示不得拖延真实Agent闭环。

### 3.3 自动化提交与人工提交

D22明确MVP GitHub只读，因此MVP审核后导出材料，人工提交并回填PR。D01/D23中的人工批准始终有效。V1受控工具方可执行写操作，且批准必须针对具体内容，不是“门禁通过就自动提交”。

### 3.4 状态与证据

D15中的STALE建议是附加标记，保留原生命周期；实现采用needs_revalidation。D27证据等级不与测试层级混用：E3仅说明问题复现，不证明补丁有效；T1静态通过不等于T2单元通过。缺少环境不等于失败，也不是通过。

### 3.5 安全不属于可延后的高级功能

D17是执行前提。Checkpoint、幂等、租约和预算虽可从简实现，不能全部推至多Worker阶段。单Worker也会崩溃和重试；本地测试也会执行不可信构建脚本。MVP只减少规模，不取消边界。

## 4. 本次新增的实施建议，非额外历史决策

| 建议 | 原因 | 允许调整方式 |
|---|---|---|
| FastAPI/Pydantic、SQLAlchemy/Alembic及轻量MVP页面 | 保持Python/LangGraph集成简单、迁移可控 | 实施时说明等价替代，不改变能力边界 |
| lease_generation fencing与提交对账 | 防止过期Worker覆盖、Checkpoint双写不一致 | 可替换实现，必须通过相同故障注入 |
| 公开投影独立存储与白名单 | 降低公开接口误泄漏风险 | 可逻辑隔离，但公开服务不可访问内部原始载荷 |
| 预算预留、审批hash、outbox | 让预算/权限/副作用可执行与可验证 | 不得移除对应约束 |
| 10—20条起步评测、阶段工作日、租约120秒/续租30秒 | 给开发可运行起点 | 按真实环境和评测调整，记录变化 |
| CLOSED_UNMERGED、UNKNOWN等补充分支 | 原讨论明确需要失败/拒绝/未知分支 | 枚举可调整，但不能丢事实或误标成功 |
